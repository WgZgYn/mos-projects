# 受检 read/readv 与流数据提交

## 问题

读取不仅是把裸指针换成内核缓冲：如果先移除管道字节，再发现用户目标不可写，EFAULT
会永久丢掉输入。本批把“取得数据”和“消费数据”之间的提交点显式表达出来。

## 方法

- `read.rs::read_user` 先检查目标地址并准备未驻留文件页，再调用文件层读取；实际复制
  在设备就绪后重新验证，期间不把用户指针转换成 Rust 引用。
- `FileOps::read_to` 接受一个可失败的内核回调。普通文件按 offset 读取，复制成功后
  File 才推进偏移；共享打开文件描述的并发偏移序列化仍是后续 VFS 工作。
- PipeInode 在锁内用 peek_slice 查看队头，回调成功后才消费字节并唤醒写者。
  回调失败不动队列。回调不进行文件缺页 I/O：文件页在进入设备锁之前准备，避免持锁睡眠。
- TTY 保存持久解码器和待交付 UTF-8 字节，失败时保留字节，成功后仅消费实际交付部分。
  目前串行化读取使用 Mutex；完整输入工作线程/等待队列与 termios 仍在后续任务。
- readv/writev 共用描述符快照与 1024 数量、总长度校验。readv 已有数据后，后续空管道
  使用非阻塞尝试并返回部分结果，不为了填满下一向量再睡眠。

## 结果和测试

`test_read_boundary` 覆盖无效地址/权限不消耗管道输入、readv 部分结果、描述符数组预检、
空向量、EOF、错误 fd、总长度溢出、普通文件失败不推进偏移、未驻留可写文件映射和 fork COW 隔离。

环形缓冲宿主测试验证跨边界 peek 不消费数据，另验证 VFS 错误码范围。QEMU runner
保留所有既有信号、TLS、SIGPIPE、write 边界和 BusyBox 管道/sh/echo 测试。

2026-09-10 最终验证：全量用户程序及完整 release 镜像构建成功；collections 的 5 个
宿主测试与 VFS 错误码测试通过。单核/4 核 QEMU 的新增读取边界和全部旧回归通过。
4 核首次启动因本机 monitor 端口绑定失败退出，改用 55604 后完成验证；没有改动或终止其他 VM。

## 后续工作

本批未实现等待取消、前台 Ctrl-C 或标准 TTY 行规程。下一批将信号待处理状态与
管道/TTY/计时等待登记关联，处理取消与正常事件竞争，避免旧等待项唤醒后来的等待。
随后按 syscall 区分 EINTR/SA_RESTART；管道 PIPE_BUF 原子性同时补充。

新的有状态设备必须实现 read_to 的提交语义，不能直接使用面向可重读文件的默认实现。
普通硬件缺页处理仍需统一“填充后发布”的协议；本批只在 syscall 缓冲准备路径完成。
